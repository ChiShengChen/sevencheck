# 自動驗證 LLM 輸出：七類技巧 Checklist

> 抽象自四個真實專案（NeuronLit・rex・hunch-it・RoboxAI，2026）。
> 每條規範都對應至少一次真實事故；出處以 `[NL]` `[rex]` `[HI]` `[RX]` 標記。
> 誠實註記：本分類法本身是 single-run——由一個 reviewer 從四份單人專案抽出，尚未被獨立驗證。

---

## 判準（先於一切）

一個 LLM 輸出「可自動驗證」，若且唯若：

> 你能寫出一個**不看生成過程、只看輸出＋既有資料**就能判 FAIL 的函式。

- 分派反射 `[rex]`：能只靠輸出物（evidence pack）偵測？能 → 寫成 check＋重現測試；不能 → 寫進 skill 或交給人。兩者擇一，不能只是修掉。
- 設計順序：**驗證器先於生成**。eval harness 第一天就寫——在那之前每次改 prompt 都是在賭 `[RX]`。
- 設計問句：「如果我以為在發生的事其實沒發生，這個輸出會長什麼樣？」然後檢查它是不是已經長那樣了 `[rex]`。

---

## ① 對源驗證（grounding）

**規範：證據必須是可機械比對的關係，不是語意相似。**

- [ ] 引用句是來源文件的 **verbatim 子字串**（byte 級比對，不是 embedding 相似度）`[NL]`
- [ ] 模型給的引用先逐字 quote，再對原文 **re-grep**；驗證失敗即整條丟棄，**絕不修補** `[rex]`
- [ ] 一切 ID（PMID／DOI／ticker／body ID）對本地權威庫 resolve；模型**永不鑄造** ID `[NL]`
- [ ] 來源快取本地化＋版本釘死，驗證不依賴外部服務當下的狀態 `[NL]`

## ② 對型驗證（結構與 render 分離）

**規範：凡「答案有唯一正確性」的值，由 code render；模型只產散文或結構化 patch。**

- [ ] schema＋validator 是唯一真理；所有寫入方（含非 Python 程式）都必須過同一個 validator `[RX]`
- [ ] 數字由 engine 從資料確定性 render 再 splice 進文稿；模型輸出裡的數字一律不採信 `[rex]`
- [ ] 模型對 UI／文件的操作用結構化 marker（如 `<action:*>`），不許自己排版；parser 可 snapshot 測試 `[RX]`
- [ ] 建置 fail-loud：缺 section、存在但未被引用的表 → 非零 exit，不產出殘缺成品 `[rex]`
- [ ] 當答案可以用 code 算出來，就不要問模型（deterministic-reply 短路）`[RX]`

## ③ 缺席驗證（最容易漏的一類）

**規範：「不存在」必須是一個可檢查的狀態，不准被 render 成一個值。**

- [ ] required-absence：沒被回答的欄位必須維持缺席——一個猜出來的「典型值」會無聲地取消掉下游本來要問的問題 `[RX]`
- [ ] 任何坐在值域邊界上的統計量（0.000、1.000、chance level）必須帶 validity flag；沒有 flag 之前**這個值不可讀** `[rex]`
- [ ] honest nulls：空結果也記錄成明確狀態（如 lit-dark＝有接線、沒文獻＝發現候選），不讓它默默消失 `[NL]`
- [ ] blockers 機制：一臂資料被判退化後，**它下游的一切**都標記為不可讀，而不是只標記它自己 `[rex]`
- [ ] 沉默不是證明：掃描回報「乾淨」時，先確認該檢查的內容真的抵達了掃描器（上游可能已把它剝掉）`[HI]`

## ④ 軌跡驗證

**規範：斷言行為軌跡，不只斷言最終輸出——被跳過的步驟在輸出裡不可見。**

- [ ] 重播互動並斷言**事件順序**（如問題順序）：捏造值會刪掉自己的問題、漏值會讓問題重複，兩者只在軌跡上可見 `[RX]`
- [ ] 每個修法配自己的**機制計數器**（觸發 N 次、救回 M 條）；計數器沒動的修法不論總量怎麼變都未被證明有效 `[HI]`
- [ ] 總量指標（總通過率、總分）只當背景雜訊帶看，永不當單一改動的證據——它的 run-to-run 波動常比任何改動都寬 `[HI]`
- [ ] coverage 雙向查：引用的都存在 ≠ 存在的都被引用（曾有五張圖 shipped 時零引用）`[rex]`

## ⑤ 獨立重現

**規範：進最終產物的結論，需要第二個獨立來源。**

- [ ] blind dual-run：兩個互相隔離的 run、同一 schema、各自產出 machine-diffable 報告 → diff → 逐條裁決分歧才准 merge `[NL]`
- [ ] 派工前先做獨立性（LEAK）檢查；對照 run 永不 merge 但保留＝獨立證據 `[NL]`
- [ ] 重放忠實度**先行**：離線重放必須先證明能重現 production 判定（如 31/31），不一致則所有結論作廢——不忠實的數字比沒有數字更糟：它們看起來像量測 `[HI]`
- [ ] 重放的單位對齊 production 的判斷單位（production 評估的是集合，就一次重放整個集合）`[HI]`

## ⑥ 陰性對照與已知答案注入

**規範：量測系統之前，先量測「自己有多容易被騙」。**

- [ ] placebo controls：常駐一組**已知無效**的產生器（如占卜 agent），只在 calibration 模式執行，量框架的偽陽性率 `[HI]`
- [ ] 隨機值壓測：把隨機數丟進驗證規則，量它有沒有牙（隨機四位小數曾 100% 通過鬆散的 reconciliation）`[rex]`
- [ ] 退化型態偵測：把「壞掉的結果長什麼樣」寫成 check——accuracy 恰等於多數類先驗、多 seed 零變異（全 1.0000）、兩臂 byte-identical `[rex]`
- [ ] grader／judge 用**負向 fixture** 保護：確認它會 FAIL 該 FAIL 的東西，而不只會 PASS `[HI]`

## ⑦ 驗證器自檢（meta 層）

**規範：檢查器也是會壞的軟體，須被同等對待。**

- [ ] 每個守衛檔頭寫兩件事：**為什麼存在**（哪次事故）＋**抓不到什麼**——第二件更重要 `[HI]`
- [ ] 誤報率是一級指標：狼來了的 check 會被人關掉，比沒有 check 更糟 `[HI]`
- [ ] test-binding：寫進 checklist 的規則必須**同一個 commit** 附上強制它的測試；沒有測試的規則只是註記 `[NL]`
- [ ] 對驗證器本身做 ⑥：丟已知壞資料進去，確認它報警 `[rex]`

---

## 四條流程律（讓以上可執行）

1. **fail-closed 是預設形狀**：白名單完整且一字不差、無萬用字元、無複合指令、越界即殺、smoke test 零 denial 才啟動 `[NL]`
2. **人工閘門放狀態機，不放 prompt**：順序不可顛倒由型別保證；「人不批准，什麼都不會發生」是機械事實不是約定 `[rex]`
3. **每個數字帶四件套 provenance**：分母、粒度、path:line、live-run 重現指令 `[NL]`
4. **改動先寫可證偽預測，再看分數**：change manifest（rootCause／predicted／atRisk／rollback，含「試過什麼沒用」）在看到新分數**之前**寫——順序反過來就是事後合理化 `[HI]`

---

## 定位

- 這套方法＝把實驗科學方法論搬進軟體驗證：⑤＝replication、⑥＝negative control、④＝process tracing。
- 與 property-based／metamorphic testing 同族，但瞄準的失敗模式不同：傳統測試防 crash，這套防「plausible 但錯」——LLM 的失敗不丟 exception，它回傳一個看起來像答案的東西。
- ③ 缺席驗證在傳統測試文獻幾乎沒有對應物，卻在四個互不相關的域各自獨立出現——本 checklist 裡最值得單獨寫出來的一類。
